版本 V0.1状态：内部评审稿日期：2026-08-23范围：Windows PC 内部测试接入平台：Jira + Perforce P4
本期核心决策不开发第二套缺陷管理平台；只解决现场信息难以完整带入 Jira 的问题。

什么是 Jira 和 Perforce P4？

Jira：Atlassian 提供的研发协作与问题跟踪系统，本项目用它管理正式缺陷工单、字段、流程、负责人、沟通和检索。

Perforce P4：游戏研发中常用的版本管理系统，本项目用它管理代码与大型游戏资产，并通过 Stream 和 P4 Changelist 追踪版本变更。

01

需求摘要


概念解释

Build ID：构建系统为每个可运行测试包生成的唯一版本标识，用于确认问题出现在哪个游戏版本。

P4 Changelist：Perforce 为一次代码或资源变更生成的唯一提交编号。

问题

缺陷现场信息不完整

试玩者手动建 Jira 单，容易漏填构建、场景、坐标和日志；QA 反复追问，研发仍难复现。

功能设计

游戏内 60 秒完成提交

按快捷键打开提交窗口；系统自动读取版本与运行环境，附上截图和日志，并创建字段完整的 Jira Bug。

系统原则

原始提交留档，工单统一在 Jira 处理

系统保存原始提交和同步记录，用于失败重试与问题排查；状态、负责人、评论、修复和回归只在 Jira 中维护。

MVP 范围

帮助研发收集完整现场信息，以便复现问题

本期不做 AI 分诊、相似缺陷推荐、崩溃归类、短视频录制和完整测试用例管理。

一句话描述：试玩者发现问题后无需退出游戏，通过快捷方式快速提交带有 Build ID、P4 Changelist、场景、坐标、截图、日志和复现描述的缺陷反馈；QA 可直接在 Jira 完成分诊，研发可据此开始复现。
02

产品MVP目标

本期优先提高首次提交的信息质量和送达可靠性；缺陷管理、版本追踪与后续协作继续复用现有系统。

本期价值取舍

  • 缩短提交路径：试玩者无需退出游戏，在 Windows 测试版本内完成缺陷填写与提交。
  • 提高首次信息质量：自动带入版本、场景、设备、截图、日志和轻量性能快照，减少 QA 补问与研发复现准备时间。
  • 保证可靠送达：保存可追溯的原始提交；断网或 Jira 暂时不可用时允许重试，并通过 Submission ID 避免重复建单。
  • 保留补充闭环：对信息仍不完整或暂时无法复现的缺陷，QA 或研发在 Jira 中标记“待补充信息”并写明缺失项；试玩者在原工单中补充后继续处理，不重新建单。
  • 不重复建设现有能力：本期不开发第二套缺陷管理后台；状态、负责人、评论、通知、修复与回归保留在 Jira，版本追踪保留在 P4 和构建系统。
未来可能规划（本期明确不做）

后续版本继续以内部研发提效为优先，并按建设方向归类；各方向内 P0 优先验证，P1 根据 MVP 数据和实际问题量决定是否建设。

用户角色与职责

权限以 Jira 项目角色为准；提交端只暴露当前角色需要的操作。

试玩者

发现并提交问题

填写问题现象和复现信息；查看提交结果；按 QA 要求补充信息。无权设置最终严重度、优先级和负责人。

QA

校验与分诊

确认问题有效性；修正分类、严重度和优先级；分配责任组；发起补充；验证修复并关闭。

研发

复现与修复

查看证据；记录复现结果和修复说明；填写目标修复版本及修复 P4 Changelist；提交 QA 回归。

管理员

维护配置与可用性

维护 Jira 字段、工作流、权限和系统账号；维护客户端配置；处理同步失败和访问授权。

06

功能来源与开发范围

下表明确哪些功能直接使用 Jira、P4 或开源组件，哪些功能需要团队开发。

概念解释

SQLite：无需独立数据库服务、将结构化数据保存在本地文件中的轻量关系型数据库，本期用于暂存未同步草稿。

zlib：常用的数据压缩库，本期用于减小文本日志体积并生成便于上传的压缩附件。

Watcher：关注某条 Jira Issue 并接收其更新通知、但不一定负责处理该问题的用户。

Automation：Jira 根据预设的触发条件和判断规则自动执行分派、通知或字段更新等动作的能力。

JQL：Jira Query Language 的缩写，是按项目、状态、负责人等条件查询和筛选 Issue 的查询语言。

Dashboard：Jira 使用筛选结果和统计组件集中展示缺陷数量、状态及趋势的数据看板。

REST API：供同步服务以程序方式创建 Jira Issue、填写字段和上传附件的标准接口。

Webhook：Jira 在指定事件发生时主动向外部系统发送通知数据的回调机制。

功能由谁提供具体做法本期结果
工单、字段、状态与权限Jira配置 Game Bug 类型、自定义字段、工作流和项目角色。所有缺陷统一记录在 Jira。
协作、通知与检索Jira使用评论、附件、Watcher、Automation、JQL 和 Dashboard。不建设独立管理端。
连接 JiraJiraREST API 创建 Issue、上传附件；Webhook/Automation 触发通知。同步服务不直接操作 Jira 数据库。
版本与资产历史P4P4 管理代码与资产；Jira 记录测试 P4 Changelist 与修复 P4 Changelist。Bug 可追溯到对应版本。
测试包版本清单构建系统构建系统在生成测试包时写入 build_manifest.json。提交端自动获得 Build ID 与 P4 Changelist。
本地草稿SQLite保存最多 20 条未同步草稿；同步成功即删除。短时故障不丢报告。
日志压缩zlib日志截取并压缩为 ZIP，单包不超过 20 MB。附件可直接上传 Jira。
游戏内反馈插件自行研发UE5 内按 F8 打开表单，采集元数据、截图和日志。试玩者不退出游戏即可提交。
提交前校验自行研发检查必填字段、自动采集结果与附件状态。现场阻止无效报告。
原始提交记录自行研发按 Submission ID 保存原始字段、附件、同步状态、失败原因和 Jira Key，保留 30 天。支持失败重试和同步问题排查。
Jira 同步服务自行研发校验身份、保存原始提交、映射字段、上传附件并返回 Jira Key。客户端不保存 Jira 系统凭证。
配置下发自行研发服务端下发项目 Key、选项、附件上限和 Jira 字段映射版本。字段变化无需重新打包。

07

MVP 功能需求

以下五项功能需要本期开发或连接；Jira 内的处理规则见第 08 节。

F01

缺陷反馈窗口

Windows 测试版本内按 F8 打开；不要求试玩者离开游戏。

自行研发

交互与规则

  1. 按 F8 后 1 秒内显示窗口，默认截取当前画面。
  2. 表单包含：标题、问题类型、实际结果、预期结果、复现步骤、发生频率。
  3. 自动字段只读展示：Build ID、P4 Changelist、场景、坐标、平台和设备摘要。
  4. 点击取消时保留当前输入 10 分钟；再次打开继续编辑。
  5. 提交期间显示各阶段状态：校验、上传附件、创建工单、完成。
验收标准
  • 窗口打开 P95 ≤ 1 秒。
  • 所有手动必填字段为空时均不能提交，并在字段下方给出原因。
  • 提交成功展示 Jira Bug Key 和“复制编号”按钮。
F02

现场信息自动采集

只采集复现最需要、且能稳定获得的信息。

自行研发

自动字段

  • 构建：Build ID、P4 Stream、测试 P4 Changelist、构建时间、引擎版本。
  • 运行：地图/关卡名、世界坐标、游戏语言、分辨率、画质档位。
  • 设备：操作系统、CPU、GPU、显存、内存、显卡驱动。
  • 性能快照：提交时的 FPS、游戏线程/渲染线程帧时间、内存和显存占用；本期不持续采集性能曲线。
  • 证据：当前截图 1 张、当前会话最近 5 分钟或最多 20 MB 的日志。
  • 每个自动字段记录采集状态；失败时显示“未采集”及原因。
验收标准
  • Build ID 与测试包构建记录一致。
  • 截图可正常打开，日志可解压且时间覆盖提交前 5 分钟。
  • 性能快照可读取；采集失败不阻止提交，并显示失败原因。
  • 单项采集失败不阻止保存本地草稿，但 Build ID 缺失时禁止正式提交。
F03

提交前检查

在问题发生现场发现缺失信息，避免不完整的报告进入 Jira。

自行研发

检查规则

  • 标题 8–80 字，格式建议“场景 + 操作 + 异常现象”。
  • 实际结果、预期结果各不少于 10 字。
  • 复现步骤至少 1 步，每步独立输入，允许排序。
  • 发生频率单选：首次、偶发、经常、必现。
  • 画面/UI/动画类问题必须有截图；当前截图默认满足。
  • 附件总大小不得超过 Jira 当前配置上限；MVP 产品上限取 25 MB。
验收标准
  • 一次列出全部错误，不让用户反复点击提交后才逐项发现。
  • 错误提示指出具体字段和修改方法。
  • 检查规则由服务端统一保存和更新，客户端读取最新版本。
F04

保存原始提交并创建 Jira 工单

客户端必须通过同步服务提交；服务端先留档，再写入 Jira。

自行研发 + Jira API

处理规则

  1. 使用公司 SSO 身份获取临时登录凭证。
  2. 服务端检查项目、字段和附件大小，以 Submission ID 保存不可修改的原始提交。
  3. 按照字段映射创建 Game Bug，并上传截图和日志 ZIP。
  4. 将 Build ID、P4 Changelist、场景等信息写入对应字段，完整环境信息写入描述中的“环境信息”部分。
  5. 将 Jira Key、链接、创建时间和同步结果写回原始记录；工单尚未创建时不能提示成功。
验收标准
  • 可通过 Submission ID 查到原始内容、附件、同步记录和对应 Jira Key。
  • 创建成功率 ≥ 99%，P95 ≤ 10 秒（25 MB 内附件）。
  • 重复点击提交只创建一张工单；通过 Submission ID 保证幂等。
  • 客户端和日志中不得出现 Jira 管理 Token。
F05

失败重试与数据保留

建议使用 SQLite 持久化未送达同步服务的提交，避免断网、超时或游戏退出导致反馈静默丢失；Jira 暂时不可用时由同步服务继续重试，并以 Submission ID 防止重复建单。

自行研发 + SQLite

处理规则

  • 请求尚未到达同步服务时，客户端用 SQLite 保存字段和附件，最多保留 20 条。
  • 同步服务接收成功后，保存原始提交并返回 Submission ID；Jira 暂时不可用时自动重试 3 次。
  • 3 次仍失败则标记“同步失败”，由管理员手动重试；不得创建重复工单。
  • 获得 Jira Key 后删除客户端草稿；服务端原始记录和附件保留 30 天后自动清理。
  • 原始记录不可编辑；如需补充或更正，在 Jira 中操作并保留历史。
验收标准
  • 断网后关闭并重开游戏，客户端草稿仍存在。
  • 同步服务已经接收、但 Jira 不可用时，无需客户端重新提交也能继续重试。
  • 同一 Submission ID 始终只对应一张 Jira 工单。
  • 到期记录和附件按日清理，并保留清理数量日志。

09

关键规则、异常与安全要求

明确失败时系统必须做什么，避免“酌情处理”成为实现缺口。

场景系统处理用户看到的结果禁止行为
Build 清单缺失停止正式提交，允许保存本地草稿；记录清单读取错误。“无法识别当前测试版本，请重启正确测试包或联系构建负责人。”不得使用“未知版本”创建 Jira Bug。
截图失败允许重新截图；三次失败后可提交，但必须手动确认。展示失败原因和“重新截图”。不得显示附件成功但实际为空。
日志超过 20 MB按时间从近到远截断，只保留提交前最近日志，并在描述中标记截断。“日志已截取最近 5 分钟，共 18.4 MB。”不得无限压缩或上传导致提交卡死。
Jira API 超时保留原始提交；按 Submission ID 查询是否已建单，未建单才重试，最多自动重试 3 次。“报告已保存，正在同步 Jira；无需重新提交。”不得直接再次创建导致重复工单。
附件上传失败不创建工单；原始提交标记“同步失败”，保留附件并提供管理员重试入口。“报告已保存，附件同步失败，管理员将处理。”不得先建空工单后丢失附件关联。
SSO 身份过期暂停提交并拉起重新认证；表单与附件保留。认证完成后继续原提交。不得以共享账号或匿名用户建单。
重复点击提交按钮立即锁定；服务端按 Submission ID 做幂等处理。只返回同一个 Jira Bug Key。不得创建多张相同工单。

凭证安全

Jira 系统 Token 只存同步服务密钥系统；客户端使用短期用户凭证，日志不得打印 Token 和完整 Cookie。

最小采集

不采集私人文件、剪贴板、账号密码和与游戏无关的进程信息；采集字段在提交窗口中可见。

访问控制

缺陷附件继承 Jira 项目权限；测试项目默认仅项目成员可见，不生成外网可访问的附件链接。

数据保留：原始提交及附件默认保留 30 天，到期自动删除；Jira 工单和已上传附件按 Jira 项目规则保留。删除原始记录不影响 Jira 工单。
